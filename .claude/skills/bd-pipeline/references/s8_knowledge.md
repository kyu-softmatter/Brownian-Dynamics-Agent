## 1. `08_conclusion.md` 구성

형식 예시: [`runs/2026-07-28_trap-2d-5um_2dfb9d/08_conclusion.md`](../../../../runs_s1s8/2026-07-28_trap-2d-5um_2dfb9d/08_conclusion.md)

### ① 질문에 대한 답 — 한 문단

S1 의 `question` 에 **직접** 답한다. 배경 설명으로 시작하지 않는다.

★ **가정 의존성을 표로 분리한다.** 첫 완주에서 이렇게 했다:

| 양 | 확정값 | 가정 의존성 |
|---|---|---|
| `⟨x²⟩` | `416.58 ± 1.85 nm²` | **없음** — `k`·`T` 만으로 결정 |
| `τ_trap` | `8.0567 ± 0.0300 ms` `× (a/5 μm) × (η/η_water)` | `a`·`η` 에 선형 |

**동적 결과를 매개변수 형태로 적으면 가정이 숨지 않는다.** 나중에 `a` 가 틀렸다고
밝혀져도 그 표만 보고 재척도할 수 있다.

### ② 근거 3줄

어떤 **측정**이 그 답을 지지하는가. 숫자와 오차를 붙인다.
"이론적으로 그렇다"가 아니라 "이 런에서 이 값이 나왔다"여야 한다.

### ③ 신뢰도와 한계 — 표로

`REPORT.md` 의 게이트 표를 인용하되, **코드가 검사하지 못하는 한계를 추가한다**:

- 모델과 실제의 대응 (HI 무시, 상수-`γ` Stokes, 균일 노이즈의 꼬리)
- 유한 `N`·`t`
- 가정의 영향 (S7b 결과)

★ **감도가 해석적으로 0 이면 런을 돌리지 않는다.** 첫 완주에서 `∂ln⟨x²⟩/∂lnη = 0`
(정확히)이므로 S7b OAT 런을 생략했고, 그 사실을 적었다. **"이 값은 결론을 바꾸지
않는다"도 결과다.**

### ④ 다음 실험 제안

이 결론을 **더 굳히거나 반증할** 최소 비용 실험 1~2개. 각각에 얻는 것과 비용을 적는다.
그리고 **왜 지금 하지 않는지**도 (우선순위가 낮다 / 측정값이 없다 / 사용자 보류).

### ⑤ 이 런이 시스템에 대해 알려준 것

**잡힌 오류를 전부 적는다.** 첫 완주에서 4건이었고 3건은 테스트가, 1건은
"FAIL 이 나왔는데 왜?" 를 파고들어서 잡았다. 이 절이 "이 봇이 가능한가"에 대한 증거다.

### ⑥ 판정 블록

```yaml
verdict_overall: PASS_WITH_INCONCLUSIVE
proposed_by: agent
confirmed_by: null            # ← 사람 확정 대기
```

## 2. knowledge 커밋 — **생략할 수 없다** (게이트)

계약: [`knowledge/wiki/CLAUDE.md`](../../../../knowledge/wiki/CLAUDE.md)

### 어디에 무엇을

| 무엇이 생겼나 | 어디에 |
|---|---|
| 질문에 답했다 | `wiki/findings/<slug>.md` |
| 답 못 했다 | `wiki/questions/<slug>.md` (`status: open`) — **지우지 않고 열어둔다** |
| 접근이 실패했다 | `wiki/findings/dead-end-<slug>.md` |
| 계를 처음 다뤘다 | `wiki/systems/<계>--<동역학>.md` |
| 문헌 검증값을 추출했다 | `wiki/benchmarks/<id>.md` |
| 파라미터 근거가 생겼다 | `wiki/concepts/<slug>.md` |
| 카드의 벤치마크가 확인됐다 | 그 카드 §8 을 `[O]` 로 승격 + 실측값 기록 |

### frontmatter 는 계약이다

```yaml
---
type: finding
author: agent
drafted: 2026-07-28
confirmed_by:                 # 비워둔다. 사람이 검토한 뒤 채운다
status: proposed
question: "…?"                # 한 문장
answer: "…"                   # 한 문장. 없으면 questions/ 로
cause_class: analysis         # findings 중 실패 사례면
runs: [<run_id>]
cites: [파일 경로들]
---
```

### findings 의 형식 — 진단 경로가 핵심이다

```markdown
## 증상        관측된 것 그대로. "이상했다" 금지 → "KS p값이 4개 조건 전부 0.0000"
## 진단 경로    무엇을 의심하고 어떻게 배제했는가. **순서대로.** 다음에 같은 증상을
               만나면 이 순서를 따라간다 — 이게 이 문서의 핵심 가치다
## 근본 원인    한 문단. cause_class 와 일치
## 처방        구체적 diff. "조심한다" 금지
## 재발 방지    추가한 테스트/가드/문서. **없으면 "없음"이라고 명시** —
               "없음"이 반복되는 유형은 가드를 만들 신호다
```

### 규율 — 어기면 위키가 소문 저장소가 된다

- **기존 항목과 모순되면 새 항목 + `supersedes`.** 조용히 덮어쓰지 않는다
- **`reproduced: no` 를 근거로 인용하지 않는다.** `[출처, 미재현]` 으로 표기
- **`finding` → `concept` 승격은 사람 승인.** 에이전트가 스스로 개념을
  인플레이션시키는 것을 막는다
- **`confirmed_by` 는 비워둔다**

### 벤치마크 승격

재현 가능한 수치는 `tests/` 로 올린다:

```python
@pytest.mark.benchmark
def test_...():
    """허용오차는 **이론 통계오차**에서 뽑는다 (관측값에 맞춰 재단하면 사후합리화)."""
```

문서 값과 대조할 때는 **문서에 적힌 유효숫자에서 허용오차를 뽑는다** —
전역 상수 하나면 느슨한 쪽이 엄격한 값을 봐준다
(`tests/test_s3_spec.py::rounding_halfwidth` 참조).
